## 2. 일자별 진행 상황

### 260708

#### 진행한 작업
- 일정 수립 완료 (간략 버전)
- Corrective RAG 그래프 구조 설계
  - `vectorstore.similarity_search_with_score` 사용 → ChromaDB 기준 유사도(거리) 반환, (document, score) 튜플 리스트 형태
  - 그래프 흐름: `initialize → search → evaluate → 라우터 → (재검색 시 research_quest 갱신) → learn → END`

#### 의사결정
1. 평가 방식 : 우선 유사도 점수를 임시 기준으로 채택, 추후 명확한 평가 기준을 마련하면 수정 할 계획
2. 재검색 시 쿼리 처리 방안 검토
   - k값 증가안 → 평균 기반 평가 체계에서는 효과가 제한적이라 판단, 기각
   - LLM에게 질문 재작성을 위임하는 안 → 성능은 기대되나 프롬프트 설계 방향 불확실, 의도 손실 우려
   - 원 질문 그대로 웹 검색 → 구현 가능성 미검증 (문서 기반 검색만 진행해본 상태)
3. 최종 방향: 문서 기반 설명 프로그램이므로 웹 검색은 신중히 적용
   - 답변 불만족 시 → ① 웹 검색 여부 확인(human-in-the-loop) → ② 승인 시 웹 검색 → ③ 거부 시 대체 질문 쿼리 적용
   - 필요 기술: human-in-the-loop, 메모리 세이버(중단 대화 이어가기), TavilySearch(웹 검색 도구 후보)

#### 완료 항목
- 유사도 점수를 document의 metadata에 반영, 평균 계산 노드 구현
- 변수 초기화 노드 구현
- 그래프 작동 로직 재작성

### 260709

#### 목표: 그래프 구조 완성

그래프 로직 (3가지 분기)

| 케이스 | 흐름 | 상태 |
|---|---|---|
| 평가 통과 | initialize → search → evaluate → 라우터 → learn → END | 구현 완료 |
| 통과 실패 (인터넷 검색 X) | initialize → search → evaluate → 라우터 → research → (평가로 복귀) | 구현 완료 |
| 통과 실패 (인터넷 검색 O) | initialize → search → evaluate → 라우터 → internet search → (평가로 복귀) | 구현 예정 |

- 반복 재질문 방지를 위한 상태 확인 변수 도입 결정 (1: 웹 검색 / 0: 자체 재검색)
- 인터럽트 기반 질의 로직 반영 필요

주요 판단
- 평가 기준의 AI 위임 여부 검토 → 자체 평가 기준 정립은 필수로 유지
- 재검색 쿼리 재작성은 LLM에 위임하는 방향으로 확정

회고
- 유사도 검색값은 거리 이므로 부등호 방향에 유의
- 노드 반환값이 LangGraph state에 반영되는 구조를 재확인 (반환 dict 설계상 `answer` 키로 종료되어야 정상 작동)
- LLM에게 질문 재작성을 위임한 결과 유사도가 실제로 개선되는 효과 확인
  - 부가 효과: 후속 질문에 주제를 명시하지 않아도 이전 맥락이 자연스럽게 이어짐 (question 값은 유지된 채 query만 변경되는 구조 덕분으로 추정) → 질문 의도 손실 우려 해소
- 메모리 관련 구현을 후순위로 밀어둔채 기능들을 구현하는데 우선하고 있었지만 인터럽트 구현을 하려면 메모리에 대해 고민해봐야 할것같음 
  - Claude Opus 활용 시 특이사항: 코드를 직접 제공하지 말라고 요청했음에도 특정 구현 방향으로 유도하는 경향 관찰. 실제로는 불필요한 분기 로직(웹 검색 노드의 무한 반복 우려)을 근거로 제시했으나, 웹 검색 노드는 평가 단계를 거치지 않고 곧바로 learn 노드로 종료되는 구조라 반복이 발생할 수 없음을 확인

완료 항목 : 라우터 기반 분기 처리, 인터럽트 로직, 웹 검색 노드를 제외한 필요 노드 구현

미해결 과제 : 웹 검색 API 선정 (추후 로컬 모델(Qwen)로 전환 시 API 의존성이 제약이 될 가능성 고려)

### 260710

목표 : 웹 검색 노드 구현, 체크포인터 적용, 모델 전환(Gemini → Qwen)

#### 웹 검색 엔진 비교 및 선정

| 엔진 | 특징 |
|---|---|
| Tavily | 월 1,000회 무료, 정제된 응답 제공, 응답 속도 다소 느림 |
| DuckDuckGo | 무료, 모듈 형식(API 키 불필요), 직접 정제 필요, 업데이트 시 오류 발생 잦음 |
| Brave Search | 월 2,000회 무료였으나 무료 플랜 폐지 가능성 있음 |

→ DuckDuckGo 선정 (API 요청 제한 회피 + 직접 정제 경험 목적)
- 반환 필드: `title`(제목), `href`(URL), `body`(본문 요약)

회고
- 인터럽트 발생 시 invoke가 중단되며, 재개하려면 `Command(resume=...)` 필요
- 원래 계획은 기능 독립 구현 후 메모리 관련 기능을 마지막에 통합하는 것이었으나, 인터럽트 기능 사용을 위해서는 메모리(체크포인터)와 병행 구현이 불가피함을 확인
- FastAPI 세션 관리까지 고려 시 작업 순서가 변경될 것으로 예상 됨
- 보통 web 검색은 tool로 빼서 agent를 만들어내는게 일반적이지만 현재 duckduckgo의 경우 호출 부분이 정확하여 llm에게 판단을 맡기지 않아도 될것 같음, agent를 도입할만한 부분이 어디인지 고민해봐야 할것 같음
